## Dépenses à venir : résultat concret

Une dépense future de 42,50 € apparaît, persiste après rechargement et se synchronise sur un deuxième navigateur dans les tests utilisant le SDK Firebase et des émulateurs isolés. Une deuxième reproduction montre cependant qu'une prévision enregistrée sur un compte secondaire reste invisible lorsque le compte principal est sélectionné dans l'en-tête : elle existe dans le stockage et apparaît dès que le bon compte est affiché. Ce cas est un problème de retour utilisateur/filtrage, pas une preuve de perte de données. Il ne permet pas d'identifier avec certitude l'incident du vrai utilisateur.

## Priorités confirmées

- Stockage navigateur plein : l'interface annonce une opération ajoutée alors que la sauvegarde locale échoue ; l'opération disparaît au rechargement. Des lectures de stockage interdites peuvent également interrompre le démarrage.
- À 768 px, même avec un compte vide, les cartes du dashboard se superposent et une action rapide peut intercepter le clic d'une autre.
- Une charge déjà comptabilisée manuellement/importée peut être débitée une deuxième fois lors de la confirmation du récurrent.
- La suppression d'un compte avec des réservations actives peut les réaffecter au compte principal sans avertissement.
- Une collision de l'empreinte d'import peut éliminer une opération différente ; des réservations depuis une épargne exclue peuvent fausser le disponible d'un compte sélectionné.
- Un viewer d'un espace partagé peut obtenir un code member encore valide depuis un document de membre lisible, quitter puis rejoindre avec des droits d'écriture. La portée démontrée concerne cet espace partagé, pas les comptes personnels ; les règles de production n'ont pas été inspectées.

Les rapports spécialisés décrivent les constats confirmés sur le snapshot initial : 12 anomalies financières (dont deux arbitrages produit), 10 constats UX/persistance (les neuf lignes du tableau UX et le filtre de compte), et trois vulnérabilités de sécurité. Les corrections effectuées ensuite sont récapitulées dans les sections « état des correctifs » des rapports spécialisés. Ce décompte historique ne décrit pas le nombre de défauts restant dans le worktree courant.

Le rapport natif Codex Security a été finalisé : une vulnérabilité moyenne de droits de partage et une faible concernant la lecture non bornée des corps HTTP du relais push optionnel. La configuration push committée est désactivée. La revue source a couvert 62 fichiers textuels actuels, sans audit exhaustif des dépendances installées ni inspection de production. Le registre signale des changements du worktree pendant la session : ils concernent les artefacts d'audit/tests, pas le code applicatif ; le rapport conserve son identité de snapshot initial.

Le rapport natif Codex Security du snapshot initial est conservé séparément dans les artefacts locaux de l’audit ; il n’est pas une validation du patch courant.

- Matrice UX de 100 configurations / 500 mesures de pages ; 74 géométries de formulaire mesurées, 26 incomplètes. Les dépassements sur données extrêmes ne sont pas 99 bugs distincts.
- Tests Firebase SDK multi-appareils, hors connexion, conflits, séparation UID et espaces partagés dans les émulateurs ; tests d'autorisation supplémentaires : 7 cas réussis, incluant des reproductions de défauts.
- Tests de courses de synchronisation : 100 profils avec changements pendant l'envoi, 442 modifications supplémentaires et 200 commits contrôlés ; 100 profils hors connexion/réessai. Transport simulé, non assimilé au test SDK réel.
- Tests UI desktop/mobile, imports/exports, wiki, fermetures, thèmes, récurrents et service worker hors connexion exécutés.
- Au snapshot initial, `npm test` : 70 tests, 58 réussis et 12 TODO reproduisant réellement des assertions incorrectes. Les assertions ont depuis été converties en tests de régression, à relancer avec le worktree courant avant livraison.

## Release V5.0.2 — 8 octobre 2026

La correction finale remplace le quota cumulatif par un roster atomique (place libérée au départ), conserve les anciens membres et stabilise les actualisations du partage. Le parcours cloud utilise de vrais clics, sans contournement JavaScript. Les tests finaux passent : 73 tests unitaires/régression ; 8 règles fonctionnelles + 11 tests de sécurité des règles ; parcours UI à 1440/1024/390/320, finances à 1440/390/320, installation/hors-ligne et intégration SDK multi-appareils. Les migrations V4/V5 et le nouveau site avec les règles V5.0.1 conservent les soldes principal/épargne et l’historique, puis permettent une nouvelle écriture synchronisée. La matrice extrême initiale complète et les téléphones natifs ne sont pas revendiqués.

Publication du site autorisée et préparée ; règles Firebase non publiées faute de session autorisée. Le client désactive les nouvelles actions du partage dans ce cas sans bloquer les comptes personnels. La correction serveur de sécurité du partage reste donc à activer séparément. Le caractère personnel/non professionnel est confirmé, l’identité/contact et les coordonnées GitHub sont documentés ; les bases légales, contrats, localisation et durées exactes des prestataires ne sont pas certifiés. Voir le plan juridique pour les points factuels encore ouverts.
